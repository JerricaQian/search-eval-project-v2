# eval-2-color-logic-single-element：单一元素色彩运用有逻辑

以 Phase2 JSON 样式色值预筛、以确定性七色测量为证据，逐元素计算有彩色数量。

---

## 你是谁

你是资深**单一元素色彩逻辑评测专家**。职责链为：**基于 `render`、`textFacts`、`visual`、`pageFacts` 的已确认边界、语义角色、排除归属和样式色值 → 扫描全部 Phase2 原子并预筛候选 → 对候选按七色归并计数 → 产出评级、问题项、测量证据、排除项和复核项**。

**证据只来自 Phase2 JSON 与本 Skill 确定性测量产物，绝不像素级主观扫描。**一个由 Phase2 分开的标题、标签、价格或字段即是一个元素；不合并相邻元素取色。七色归并与渐变计数规则见 `references/7色标准.md`。问题项口径：命中**达标或不达标**档位的组件/元素记为一个问题项，优秀不是问题项；同一元素只保留一个评级，不因多个色格倍乘。

---

## 触发场景

- 输入形态：已验收单图 Phase2 JSON、元素语义边界与已确认样式色值；非中性色候选的当前截图语义裁剪与测量产物。
- 关键词：颜色数量、标签色数、渐变色阶、七色、红橙黄绿青蓝紫、颜色克制、有彩色数。
- 场景变体：单一标题、独立标签、价格、评分、按钮、提示条；不含商家/下挂图片、营销图片、banner/腰封、金刚图标、元素外背景与相邻元素。

---

## 评审契约（开工前必读）

评审对象是单一 UI 元素的有彩色数量，不是整卡主色、商家图或营销大图。

1. **读取 `references/7色标准.md`；仅按本 Skill 的对象、排除项、阈值和 `aggregate` 评级。**
2. **完整遍历全部 Phase2 原子且不擅自合并。**标题、每个独立标签、价格、评分、按钮、提示条均各自成元素；相邻标签、卡片背景和照片像素不得并入目标裁剪。
3. **Phase2 事实与确定性测量优先。**JSON 样式色值、边界、背景 mask、当前版本或脚本产物任一不可信时，回退 Phase2 并停止该元素结论；不能以“看起来颜色不多”给优秀。

---

## 评审流程（4 步）

### Step 1：读取 Phase2 JSON，确定评测目标

- 记录全部 Phase2 原子的 `elementId`、`componentId`、`phase2Boundary`、语义角色和已确认 `visual.textColor/backgroundColor/borderColor`。
- 执行时直接分出 `coloredCandidateIds`、`neutralExcludedIds` 与复核项；仅候选测量行和必要排除证据进入输出，`prefilterEvidenceSource=phase2_json_visual_colors`。
- 只有上述三个样式色值中至少一个为非中性色的 UI 元素，才进入像素测量候选集；标签本身不排除。

### Step 2：先排除，再确认候选与计数例外

1. **先排除：**黑、白、灰及低明度/低绝对色度的近黑、灰褐、灰蓝等感知中性色记为 `excluded:neutral_json_prefilter`，不运行裁剪或颜色脚本；商家/下挂图片、营销图片、banner/腰封、金刚图标、元素外背景与相邻元素亦排除。
2. **再确认候选：**仅非中性色候选进入语义边界测量；若当前 Tab 没有任何非中性色候选，本项直接为优秀，并保留空候选集与全量排除记录。
3. **最后处理例外：**中性色不进入颜色格，但保留在元素有效面积分母中；占元素有效面积小于 3% 的有彩抗锯齿/压缩杂色不计。圆角元素四角露出的页面底色必须以脚本背景排除参数去除；元素自身有彩底色必须保留，不能用四角取色把标签底色误删。

### Step 3：只对候选测量并保存原始证据

- 必须仅对非中性色候选运行 `scripts/count_element_colors.py`，在语义边界内取样；不得对全部中性色元素无差别跑脚本，也不得用整卡、旧裁剪或目测替代候选测量。
- 保存原始七色归并、面积占比、调试 mask、参数和产物路径，以及中性/有彩像素数、`rawColorGrid`、`colorCount`、`measurement.tool/artifactPath/parameters`、`sampleMask`。
- 核查调试产物没有混入照片/相邻对象；裁剪混入相邻标签时必须重裁，不得在错误 mask 上解释结果。每次只以当前截图重新取样；1.0/2.0 或其他批次的颜色、色数和结论均不可复用。

### Step 4：覆盖校验、评级与问题投影

1. **先校验覆盖完整性：**每个 Phase2 原子都有候选、排除或复核记录；边界或测量失败即阻断该元素颜色结论并重取样，**有复核项停止评级**，不能静默遗漏。
2. **再先归类后读数：**同色相深浅合并到红、橙、黄、绿、青、蓝、紫之一；紫红归紫、黄绿归绿。渐变跨越一个色类计一色、跨越多个色类按多个色计；统一门槛为 `S≥15、V≥20、RGB绝对色度≥20`，任一项未达到即作为感知中性色排除。处理渐变和 1% 阈值时，仍以本 Skill 明定的有效面积小于 3% 杂色排除口径为准。
3. **最后按阈值判级并落问题项：**≤ 2 为优秀，3 为达标，> 3 为不达标；达标或不达标元素各计一个问题项，优秀不计。`rawColorGrid/colorCount` 是评级证据，不能由 LLM 修改；文本解释只能说明脚本测得的色数和色系。

- 每个问题行写目标原文、排除后的色数、中文色系和证据路径；日常评测只输出**评级 + 问题项数**，不输出“评级分布汇总（按搜索词×Tab）”或分数。
- **除本 Step 3 明确要求的 `scripts/count_element_colors.py` 外，禁止运行脚本；重构与复核本文件时禁止运行脚本。**

---

## 判定标准

| 有彩色数（排除后） | 评级 |
|---:|---|
| ≤ 2 | 优秀 |
| 3 | 达标 |
| > 3 | 不达标 |

底色、文字色和元素内部 UI 图形均计入。按红、橙、黄、绿、青、蓝、紫七色归并；渐变跨越一个色类计一色、跨越多个色类按多个色计。**达标或不达标元素各为一个问题项，优秀不是问题项。**

原阈值锚点：优秀上限 `≤2`，不达标起点 `>3`。

## 输出格式模板

📐 **单一元素色彩逻辑评测结果**

📌 **评测概述：** 搜索词 {X} · {Tab名} · 有效着色候选元素 {N} 个

Phase5 问题卡由 `assessmentRows` 中评级为达标或不达标的问题行一对一生成：`description` 写该行事实、命中规则、评级原因与直接影响；`recommendation` 写“调整对象 + 具体动作 + 本 Skill 优秀档验收条件”；Phase4 回写 `evidenceImage`。

原有字段与示例锚点（保持原口径）：`rating`、“不达标”、“优秀”。

---

**评测明细（assessmentRows）**

| 元素 | 所属组件 | 标签/元素文案 | 颜色（列举） | 色数 | 评级 |
| --- | --- | --- | --- | :---: | --- |
| 标签元素 | 商卡2 | 立减 8 元 | 红、黄 | 2 | 🟢 优秀 |

**填写示例：** 上表最后一行展示真实文案、实际数量和对应评级；正式输出时逐一替换为当前页面事实，不使用内部 ID 充当用户可读文案。

> `description` 必须以可读对象定位开头：商卡内问题写“商卡N · {名称} · {区域/元素}”，图筛、快筛等非商卡问题写其组件名称；跨卡关系必须列出全部涉及商卡。随后写实际事实、计数或比较结果、命中规则、评级原因与直接影响；不得只写内部 ID、“该组件”或“该元素”。`recommendation` 必须给出调整对象、具体动作和本 Skill 优秀档验收条件。

**建议示例：** `减少“立减 8 元”元素中的有效颜色并统一同类着色；验收时确认颜色数不超过 2，评级达到优秀。`

| 元素 | 标签/元素文案 | exclusionCode | 排除原因 |
| --- | --- | :---: | --- |

**Phase2 复核项（phase2ReviewCandidates）**

- 列出 `elementId`、背景 mask、边界、当前版本或测量产物缺口与重取样动作；存在复核项时停止评级。
- 复核项只承载当前 JSON 中未确认、归属缺失或事实不完整的对象；**存在复核项时不得给出正式评级**。

**总结说明：** 汇总达标与不达标元素的超阈颜色特征、优秀元素的色彩特征与改进建议；达标或不达标元素计问题项。 Phase5 只展示达标/不达标问题项；优秀仅保留评级解释，不进入发现问题或治理项。

## Gotchas

- **黄底黑字标签 ≠ 整枚标签排除**；至少有一个黄色系，黑字不计。
- **标题与旁边标签 ≠ 同一元素**；一排独立标签也不能合成一个“大元素”。
- **采样产物模糊或边界漂移 ≠ 可沿用历史颜色结论**；应回到当前截图重取样。
